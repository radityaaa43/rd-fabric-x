# S13: FSC node + endorser per org (fabricx), custody pieces

Status: repo only. Nothing here touches a cluster. Source: final-design/fabricx/PLAN.md S13 (DELTA 10, 1).

## Pieces
1. `core_rewrite.py`: `per_org_core(core, node, home, pod_root) -> (core, manifest)` turns the NWO-generated `~/.fabricx-token/live/<node>/core.yaml` (local template) into the per-org core.yaml. Private files only under `own/<node>/` (the issuer and endorser-1 share one pod), other nodes only as public certs under `public/`; another node's private path or an unclassified host path is REFUSED. `fsc.client.certs` = the node's own `<node>-admin` cert (`own/<node>/fsc/admin.pem`), replaced by the org's fx-gw client cert in S16; never the central Admin@fsc cert. Committer endpoints = the org's own `committer-sidecar:5130` / `committer-query-service:5140` (S12). MSP ids org1..org4.
2. `enroll_fsc.py <party> rd-fabricx-<party> --kubeconfig K --ca-url http://localhost:<port> --work /dev/shm/<dir> --exchange <dir with org<N>/msp/{cacerts,knowncerts}> --out <new>/org<N> [--generation TAG]`: identities at the org's OWN CA (all type client, not removable): `<node>-fsc`, `<node>-admin` (cert only), `<node>-id` (issuer/banks), `endorser-<N>-tls` (endorsers). ONE Secret `rdbi-<pod>-files` (pods bi, bank2, bank3, bank4; `kubectl create`, keys = pod paths with `/` as `__`, `secret_key()`/`secret_path()`) and a public tree (`fsc/<node>.pem`, `admin/<node>-admin.pem`, `ids/<node>/msp/{signcerts,cacerts}`, MANIFEST). Same custody rules as enroll.py/make_secrets.py. `ids/endorser-<N>/msp` is the EXISTING Secret `fsc-endorser-<N>-secret` (the genesis known_certs identity; never re-registered or copied), to be mounted by the render.
3. `render.py <party> --templates <~/.fabricx-token/live> --fsc-exchange <enroll_fsc --out parent> --tls-exchange <exchange with tlscacerts> --image <digest> --p2p-ips FILE [--central-keys FILE] [--storage-class SC] [--p2p-lb-acl acl-ID --p2p-lb-range <ip>/32]`: stdout only. ConfigMap rdbi-public (all nodes' public certs + TLS CA bundle), ConfigMaps rdbi-core-<node>, Services <node> (grpc/p2p/web), PVC rdbi-<pod>-state, NetworkPolicy rdbi-traffic (grpc only from fx-gw-<N>, P2P from anywhere because the CLB ACL filters and eTP Cluster hides the source, egress DNS + same namespace + the orderer and P2P addresses, NO rdbi-driver rule), Deployment rdbi-<pod> (Recreate, PSS restricted, init container `layout` copies the files under $T like k8s.py did from a tarball, hostAliases for the other orgs' node names and for the `*.arma.rd` router/assembler names). The P2P LoadBalancer Service is NOT rendered unless `--p2p-lb-acl` is given (existing ACL id only, /32 ranges only, externalTrafficPolicy Cluster); creating it is its own CLUSTER-OP line. A private path of the core that no volume item covers REFUSES the render.
4. `import_central.py <party> rd-fabricx-<party> --kubeconfig K --templates <live dir> --home <~/.fabricx-token> --keys-out <file.json>`: own-only import of the material that stays CENTRAL until S15: `ids/anon/msp` (shared Idemix submitter material), the Idemix owner wallet of each bank node, the issuer wallet MSP. For each node of the org it reads ONLY the directories that node's own core.yaml names (via `core_rewrite`), refuses symlinks and empty dirs, and `kubectl patch secret rdbi-<pod>-files --type merge --patch-file /dev/stdin` adds the files as base64 `data` keys `own__<node>__<path>` (values only on stdin, never argv). `--keys-out` holds the key NAMES for `render.py --central-keys`. Layout smoke (`test_layout_smoke.py`): applies the rendered volume items like the pod's `layout` init and checks that every path in every rendered core.yaml exists; run over the 8 REAL local templates with the real central file names it found 0 uncovered paths. It found one real gap while being written: the core's resolver `lib-p2p-bootstrap-node` names a PUBLIC cert file the node reads at start, so `render.py --bootstrap-cert FILE` is now required (source: the public `.../peers/lib-p2p-bootstrap-node.fsc.example.com/msp/signcerts/*-cert.pem` of the local livegen tree, a certificate only).

## Pod layout (what the render must produce)
`$T/own/<node>/{fsc/{cert.pem,key.pem,tls.crt,tls.key,tls-ca.crt,admin.pem},tls/{cert.pem,key.pem},ids/<node>/msp/...}` from the Secret items (`secret_path()` restores the sub-path), `$T/public/...` from ConfigMap `rdbi-public` (the other orgs' public trees + all four TLS CAs), `$T/live/<node>/{data,trace.out}` = the PVC.

## Import of the central material: two facts found on the first live attempt (2026-11-12, stopped with 0 writes)
- File names: the issuer wallet MSP holds `admincerts/issuer@Orgissuer.example.com-cert.pem`; `@` is not a valid Secret key character, so `import_central.py` sanitizes every character outside `[-._a-zA-Z0-9]` to `_` in the KEY (and so in the pod file name) and refuses two files that collide afterwards. This is safe because an MSP directory is read by directory scan, not by file name: `fabric-x-common msp/configbuilder.go` `getMspConfig` loads `admincerts` with `getPemMaterialFromDir`, which reads every file of the directory.
- Mechanism: the party-admin Role has `create/update/patch` on secrets but NO `get`, and `kubectl patch` GETs first (Forbidden). The tool therefore sends ONE direct API call `PATCH /api/v1/namespaces/<ns>/secrets/rdbi-<pod>-files` (merge-patch+json) with the party kubeconfig's own server/CA/token, read in memory, never on argv or in output, error text scrubbed. Same credential, verb and object as `kubectl patch`; no RBAC change; no cluster-admin credential.

## P2P LoadBalancer Service (render --p2p-lb-acl): shape
`service.beta.kubernetes.io/backend-type: eni` is part of the S10b shape the orchestrator approved (with `externalTrafficPolicy: Cluster`, existing ACL ids, ACL annotations in the FIRST apply). It is a CHOICE, not a proven dependency of the ACL/listener: besu's live zeto besu-p2p Services on bank-a and bank-b carry only the three ACL annotations with eTP Local and no eni and bank-c peers through them (rd-besu `zeto/k8s/paladin/README.md`, "S10" and "S10b run notes"). The `100.64.0.0/10` health-check element of the pod NetworkPolicy is added only AFTER the annotation/listener read-back; positive control from the OTHER cluster's egress /32 and the hosted-runner negative need pods behind the Service.
